# Nocturne security implementation

This is a small Electron browser prototype, not an independently audited replacement for Chrome or Edge. No component guarantees that a site or file is safe. Protection can be disabled in settings; statuses describe what actually ran.

## Implemented protections

- Chromium sandbox is enabled globally and for site renderers. `site-per-process` is enabled. Site content has no Node.js integration or privileged preload. Context isolation and web security remain enabled; mixed insecure content is not explicitly allowed.
- Privileged IPC checks the exact shell webContents, main frame and local shell URL. The shell blocks navigation, new windows and webviews. Site navigations and redirects are limited to HTTP(S). Popups are translated into tabs with limits (five per origin window per minute, forty total tabs). Unhandled permissions are denied; configured camera/mic, notifications and geolocation requests require native confirmation on a main HTTPS site.
- HaGeZi TIF Mini checks domain suffixes on all site network requests, including redirects, frames, resources and download requests. HaGeZi Multi Light filters third-party ads/tracking requests. First-party/third-party classification uses the Public Suffix List through `tldts`, including private suffixes. Tracker exceptions apply to the top-level site and never bypass the threat list. These are domain filters, not full uBlock-style cosmetic/scriptlet filters.
- Bundled copies work offline. Updated lists are downloaded over HTTPS every eight hours, or manually. New lists are bounded and validated before atomic replacement; failed updates retain the old lists. HTTPS delivery is used; there is no separately signed list manifest. Each list's GPL-3.0 license and attribution accompany it.
- Main-frame HTTP on external hosts is stopped behind an explanation. Users can try HTTPS or explicitly permit that HTTP origin for this run. Loopback/localhost is exempt for local apps. There is no silent fallback from HTTPS or certificate-error override. A successful HTTPS connection does not establish a site's honesty.
- Optional Google Safe Browsing v4 / Web Risk checks run for navigations/redirects and download source chains. Disabled without opt-in; requires an API key. Lookup sends full URLs, excluding fragments and embedded credentials, to Google. Private IP literals, loopback, single-label and common local suffixes are excluded; this is not a DNS-based local-network detector. Keys use OS encryption and never appear in UI status. Cloud checks fail closed when enabled but unavailable. Clean verdicts are cached for one minute and threat verdicts for five minutes. Safe Browsing API is noncommercial; Web Risk is the commercial integration. This does not implement Chrome Enhanced Protection or SmartScreen.
- Personal onboarding links to the official console/help. Explicit connection tests send only the fixed `https://example.com/` test address and bypass the local verdict cache. "Check and enable" enables protection only on success; it does not provision a Google Cloud project or key. HTTP/API failures are mapped to fixed explanations and do not expose the key or arbitrary server error text. Status distinguishes a saved key from an actual successful API response.
- Downloads are never executed automatically. Source chains are checked; files are paused while that check runs. Downloaded files receive Windows Zone.Identifier (Internet Zone) when supported. Query strings and credentials are omitted from that metadata.
- Automatic download names strip Windows-invalid characters, trailing dots/spaces and bidi controls, and avoid reserved device names. Executable/script/installer/shortcut/disk-image suffixes and bidi-spoofed names require an extra confirmation even after a clean scan. This is not content-type detection or comprehensive executable-format analysis.
- Defender scans use the current local MpCmdRun executable with `-Scan -ScanType 3 -File <path> -DisableRemediation`, via `execFile` with an argument array and no shell. Scans run serially, have a timeout, and do not change Defender configuration or request elevation. The user is not shown a clean result when scanning fails or Defender is absent. Nonzero results conservatively block opening from Nocturne because Defender's result code can mean a detection or a scanning error. Files are not automatically deleted or quarantined by this integration. Windows real-time antivirus may independently take action.
- SHA-256 before and after scanning detects changes during the scan; opening checks the current fingerprint and rescans changed files. This does not prevent an attacker already running as the same Windows user from racing local file operations. Symlinks/nonfiles are rejected by fingerprinting. Clean means "Defender reported no threats", not a safety guarantee. Executable/script extensions still require confirmation. Unavailable scanning requires an explicit "open without checking" choice. Users can still access files outside Nocturne; it is not an OS-wide execution policy.
- Security log retains only domains, reasons and timestamps in memory for the current run. No browsing URLs or API keys are sent to analytics.

## Packaged build

Automatic password migration is explicitly started by selecting browsers and clicking Import. Discovery reads paths and metadata only. NSS reads selected Firefox/Zen profiles in read-only mode through the installed browser library; primary-password authentication is required when configured. Chromium imports read-only Login Data using current-user Windows DPAPI / AES-GCM v10/v11. App-Bound v20 and unknown formats are not bypassed. This is local user-authorized migration, not an unattended background scan. A non-elevated PowerShell helper exchanges credentials through inherited stdin/stdout pipes; plaintext credentials and primary passwords are not written to temporary CSV/JSON files, networked, logged, or sent to the renderer. Only aggregate results reach the UI. Destination encryption is checked before reading source secrets. Native integration tests create independent synthetic NSS and Chromium databases and verify the source key database remains unchanged. NSS loading depends on an installed, compatible browser library and Windows policy; failures are reported without claiming success. Secrets necessarily exist briefly in process memory and cannot be guaranteed inaccessible to a compromised same-user process.

`npm run package` builds `release/Nocturne-win32-x64/Nocturne.exe` with Electron Packager and ASAR integrity metadata. Then the build disables RunAsNode, Node options/environment injection, and Node CLI inspection; enables cookie encryption, ASAR-only loading, and embedded ASAR integrity validation. Site DevTools can be opened manually with F12; remote-debugging and insecure Chromium startup switches are disabled in packaged runs. The source-development executable is not modified.

The build is **unsigned**. Fuses/ASAR verification help detect changed application contents, but an attacker with local write access can replace an unsigned executable too. A publisher certificate and trusted release infrastructure are necessary for authenticated releases and signed automatic updates; neither is fabricated. A manual runtime-version check is available and never installs code.

The packaged build defaults to `%APPDATA%/NocturneSecure`, separate from the source-development profile. This avoids opening the same cookie database with incompatible encryption fuse settings. Existing profile files are not migrated or deleted. An explicit `--user-data-dir` is respected for testing/isolated profiles. Do not alternate source and packaged runs against the same profile. Existing password CSV import works independently in either profile.

## Verification

- `npm test`: URL handling, domain suffix boundaries, PSL classification, tracker exceptions, HTTP gate, cloud opt-in/cache/outage cases, filter-update failure, simulated scanner detection/error/mutation cases, existing encrypted-vault tests.
- `node tests/security-smoke.cjs`: real Electron request interception, harmless `.test` domain fixtures, redirect blocking, tracker request, HTTP confirmation, renderer sandbox/no privileged bridge, actual OS key encryption, mocked cloud-threat/outage responses, real Defender scan of harmless text, NTFS Internet Zone marking, and safe file opening (system opener stubbed).
- `node scripts/verify-package.mjs`: packaged boot in an isolated profile, exact fuse values, a deliberately modified ASAR being rejected, and restoration of the original archive. No malware is used.
- Existing smoke, feature and settings tests remain available. Tests use isolated profiles under `artifacts/`.

## Remaining work

Publisher signing and authenticated auto-updates, independent security review/fuzzing, broader download reputation, account synchronization and extension security, and stronger credential-vault unlocking. Local list and cloud results can contain false positives and miss newly created threats. OS compromise and a malicious same-user local process are outside this browser's security boundary.

## User-initiated release updates

The About page checks the fixed public GitHub repository only after an explicit click. Stable versions must increase numerically. An installer must have the exact repository asset URL, expected name, bounded size and GitHub-provided SHA-256 digest. Streaming downloads enforce size and checksum before Defender scanning. Installation requires a separate click and another file hash verification; a blocked scan cannot launch. If Defender is unavailable, the main process requests confirmation. The ordinary per-user Inno installer runs externally and the current app quits; no silent background installation or signed publisher authenticity is claimed. SHA-256 from GitHub authenticates consistency with that service, not an independently signed publisher; a compromised repository/account remains a supply-chain risk.
